# Customers

Management Dashboard "Customers" module (Customer Management → Customers), extracted into an `md-extensions` federated remote (COP-7185, epic COP-5597). React + Vite, using the [vite-plugin-federation](https://github.com/originjs/vite-plugin-federation) Module Federation implementation.

Scaffolded from [md-module-template](https://github.com/emporix/md-module-template) (`md-module-migration` branch); Tier 1 infrastructure (providers, tenant-switch guards, column visibility, mixins, audit log, restriction parsing, customer API hook) is aligned with `companies`. See the `md-module-extraction` skill at the repository root for the workflow.

## Screens

Hash routes inside the remote (`src/constants/paths.ts`), mounted by the host on `/apps/management/customers/*`. They mirror MD's former pathname routes; the host redirects old `/apps/management/customers/<id>` links into the hash.

| Path           | Screen                                                                                                                                                                                                       |
| -------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `/`            | List: lazy table (id, first name, last name, email, preferred site) with filters and sorting, newest first; `ext_customers` column visibility with customer mixin columns; row edit and delete, batch delete |
| `/add`         | Create a customer (initial password, typed or autogenerated)                                                                                                                                                 |
| `/:customerId` | Edit a customer: details (restriction, segments, companies, groups, marketing information, assisted buying), addresses with address mixins, customer mixin tabs, audit log (`?tab=` selects a tab)           |

`Customers Viewer` can view; `Customers Manager` can create, edit and delete. The audit log tab needs `Audit Log Viewer`; assisted buying needs the `customer.assistedBuying_manage` scope and the `DCP_ASSISTED_BUYING` feature toggle. Restrictions come from the `customer.customer_manage` / `customer.customer_read` scopes. The remote loads permissions itself (`PermissionsProvider`). Segment, company and customer-group links leave the remote for the host (`window.location.assign`).

API calls: customer and address calls (`getCustomers`, `addCustomer`, `updateCustomer`, `patchCustomerCall`, `addCustomerAddress`, …, `getAssistedBuyingLoginCall`), plus `fetchCoupons` (referral coupon), `getAllGroupsForUserCall`, `getSegmentsCall` and the `restrictions` / `enableSyncBetweenRestrictionsAndSiteCodes` configurations, all from `@emporix/api-calls`, bound to the host tenant in `src/hooks/api/`.

## AppState

When the module is embedded in the Management Dashboard, the host passes an `appState` prop to `RemoteComponent`.

| Field             | Type                       | Description                                    |
| ----------------- | -------------------------- | ---------------------------------------------- |
| `tenant`          | `string`                   | Current tenant identifier.                     |
| `language`        | `string`                   | UI language from the dashboard (`en` or `de`). |
| `token`           | `string`                   | JWT access token for Emporix API calls.        |
| `currency`        | `Entry`                    | Active currency.                               |
| `contentLanguage` | `string`                   | Content language selected in the dashboard.    |
| `user`            | `User`                     | Logged-in user.                                |
| `onError`         | `(error: unknown) => void` | Host error handler.                            |

`src/models/AppState.model.ts` defines the fields this remote reads. Read them through `useDashboardContext()`. The shared `@emporix/api-calls` client is created in `src/api/bootstrap.ts` from `VITE_API_URL`.

## Development

### Environment variables

Copy `.env.example` to `.env` and set:

- **VITE_API_URL** – Base URL for the Emporix API (e.g. `https://api-develop.emporix.io`).
- **VITE_DASHBOARD_ORIGIN** – Dashboard origin the build checks against the CORS list in `vite.config.ts`.

### Checks

```bash
npm install
npm run typecheck
npm run lint
npm run test:run
npm run build:dev
```

### Loading the remote in the Management Dashboard

The remote runs on a fixed local port, `5184` (`server.port` and `preview.port` in `vite.config.ts`, `strictPort: true`). The dashboard's `.env.local-*` files point `VITE_CUSTOMERS_URL` at `http://localhost:5184/assets/remoteEntry.js`.

```bash
npm run build:dev
npx vite preview --mode dev
```

Then start the dashboard with `serve:local-qa` (or another `local-*` mode) and open `/apps/management/customers`.

Every `build*` script first runs `scripts/ensure-cors-origin.mjs`, which checks that the dashboard origin for that mode is in the `corsOrigins` list of `vite.config.ts` (`npm run check:cors -- --mode dev`).

### Standalone

```bash
npm run dev
```

The dev shell asks for tenant, token and language.

### Deploying

Firebase Hosting targets `emporix-customers-develop`, `emporix-customers-stage` and `emporix-customers` (root `firebase.json`, `.firebaserc`). Workflows: `.github/workflows/customers-firebase-*.yaml` — a preview per PR, dev and stage on merge to `master`, prod on a `customers-*` tag. The Firebase Hosting sites must exist before the first deploy.

## UI

No PrimeReact, PrimeFlex or PrimeIcons dependency. UI comes from `@emporix/component-library` (≥ 2.26.0 for the password `InputText` eye toggle; `Chips` and `SplitButton` since 2.20.0), whose stylesheet is imported once in `RemoteComponent.tsx`; feature styles are SCSS Modules. See `docs/CL_WIDGET_STATUS.md` for the component-library equivalent of each PrimeReact widget.
